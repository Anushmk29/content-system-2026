# End-to-end QA — 15 November 2026

**Implemented since this audit:** proof-link editing, safe claim correction/removal and automatic QC after drafting. See the [fix verification](CLAIM-WORKFLOW-FIX-2026-11-15.md). The findings below preserve the original audit results.

**Later blocker-only retest:** Postiz connectivity is now working. Production settings, proof-link handling and the draft-to-approval handoff remain blocked. OpenRouter was excluded. See the [focused retest report](QA-BLOCKERS-RETEST-2026-11-15.md) for the latest status; the observations below describe the original audit.

**Verdict: the application builds and its automated tests pass, but the configured system is not ready for reliable daily operation.** Real writing and image calls are blocked by OpenRouter credits; Postiz is unreachable; production configuration is rejected. Two workflow gaps prevent the promised self-service content-to-approval process even after those integrations are restored.

This review used Chromium browser automation, actual HTTP requests, live configured AI adapters, an isolated Postgres-compatible database with the real schema, source inspection, and the Impeccable technical-audit checklist. It is an engineering and heuristic UX review, not a usability study with customers.

## Findings in priority order

### 1. P0 — Production settings prevent the workspace from serving

**Reproduce:** build successfully, start the production build, then request `/content`. The response is 503: `CONTENT_RUN_SECRET and CONTENT_ADMIN_SECRET must be at least 16 characters.` Both configured passwords fail that requirement; `CONTENT_SESSION_KEY` is also absent.

**Impact:** a successful build does not mean this environment can be deployed. Development mode deliberately permits this configuration.

**Action:** configure sufficiently strong client/admin passwords and a session-signing key of at least 32 characters, then repeat a production smoke test. Credentials were not changed during QA.

Source: [production configuration guard](../../src/app/content/_lib/auth.ts).

### 2. P0 — Provider credits block the core writing and design workflows

**Reproduce:** ask the configured main model to draft, extract a voice guide, analyse an example or generate an image. OpenRouter returns 402. The production drafting limit was unaffordable with the remaining provider balance.

**Impact:** users can browse and select content but cannot reliably produce the next posts. A successful cheap-model or Jev call does not prove the writing model is usable.

**Action:** restore sufficient OpenRouter credits and retest actual drafting, scripts, voice, vision and image generation. Do not treat a smaller diagnostic prompt as proof that normal product requests work.

Source: [AI adapter](../../content-pipeline/src/adapters/claude.ts).

### 3. P0 — Postiz is unreachable

**Reproduce:** inspect live integration health. Postiz reports `error: fetch failed` while the database and several other adapters connect.

**Impact:** actual publishing and calendar-to-Postiz synchronization cannot be certified. Simulated scheduling passing is not a substitute for this integration.

**Action:** restore the configured Postiz service, verify channels, then use a controlled test destination to check schedule/move/cancel and retrieval of actual post metrics.

Sources: [Postiz adapter](../../content-pipeline/src/adapters/postiz.ts), [calendar synchronization](../../content-pipeline/src/services/calendar-sync-service.ts).

### 4. P1 — Users cannot attach the proof that blocked claims require

**Reproduce:** open a post containing an unproven claim. The drawer displays the claim and says it blocks publication, but offers no proof-link field or action. The real QA fixture could be approved, but the SQL publish-ready view correctly kept it blocked.

**Impact:** the safety gate works, but the user cannot resolve the block from the platform. Removing a claim from the visible copy also does not provide a workflow for managing its stored claim record.

**Action:** add a validated proof-link action and a clear claim-review/resolution flow. Preserve the existing publication gate.

Sources: [claim display](../../src/app/content/_components/ItemDrawer.tsx), [approval controls](../../src/app/content/_components/editors.tsx), [publish-ready gate](../../db/schema.sql).

### 5. P1 — “Draft them now” does not carry drafts into Approvals

**Evidence:** the Ideas guidance says drafts appear in Approvals, but its button calls only `draft_generator`. The single-module API runs only that module; the generator creates `draft` items. `qc_gate` is the separate stage that submits them for approval.

**Impact:** a user can follow the page instructions and find nothing new in Approvals. They must discover the separate quality-check operation. This finding is traced from the implementation; successful live drafting was blocked by credits.

**Action:** make the primary drafting action perform drafting followed by QC, or clearly expose the required next step and destination.

Sources: [Ideas instructions and action](../../src/app/content/ideas/page.tsx), [single-module route](../../src/app/content/api/modules/[id]/run/route.ts), [draft generator](../../content-pipeline/src/modules/draft-generator.module.ts), [QC gate](../../content-pipeline/src/modules/qc-gate.module.ts).

### 6. P1 — Review drawer does not receive keyboard focus

**Reproduce:** open a post from the approval list using its review link. Browser focus remains on the background link; it does not move into the drawer. The drawer has `role="dialog"`, but lacks modal focus handling.

**Impact:** keyboard and screen-reader users can continue through background content instead of the review controls. Escape works when focus is outside editable fields, but this does not resolve focus placement or containment.

**Action:** give the drawer appropriate modal/non-modal semantics, move focus to its heading or first suitable control, contain focus for a modal presentation, and restore focus on dismissal.

Source: [ItemDrawer](../../src/app/content/_components/ItemDrawer.tsx).

### 7. P1 — Small metadata text has insufficient contrast

**Measured:** against the actual cream page background, `--faint` text has contrast **2.31:1**, warning text **3.28:1**, and success text **3.66:1**. Normal-size text requires 4.5:1 for WCAG AA. Main ink is 17:1 and muted text is 4.82:1.

**Impact:** the small dates, hints and status metadata using these colors are harder to read. Decorative lines and purely graphical accents should be evaluated separately from text.

**Action:** darken semantic text colors while keeping the incumbent visual identity.

Source: [theme tokens](../../src/app/content/_styles/theme.css).

### 8. P2 — “LLM ok” currently means only that a key exists

**Evidence:** the adapter reported `ok: openrouter key present` at the same time actual writing calls returned 402.

**Impact:** the integration indicator can reassure users while a key workflow is unavailable.

**Action:** label presence separately from verified operability and surface recent authentication, credit and provider failures without paying for a model call on every page view.

Source: [adapter health check](../../content-pipeline/src/adapters/claude.ts).

### 9. P2 — Sign-out is unavailable on mobile

**Reproduce:** use a 390px viewport. The horizontal navigation works, but the sign-out control is not visible. The mobile stylesheet hides `.side-foot`, which contains the only sign-out button.

**Impact:** a mobile user has no visible way to end the session.

**Action:** expose sign-out through a mobile account/menu control.

Sources: [navigation footer](../../src/app/content/_components/Nav.tsx), [mobile CSS](../../src/app/content/_styles/theme.css).

### 10. P2 — Login returns 500 for JSON `null`

**Reproduce:** `POST /content/api/login` with content type JSON and body `null`. The response is 500 because the route destructures `password` from `null`.

**Impact:** malformed unauthenticated input becomes an internal server error instead of a controlled validation/authentication response.

**Action:** validate the parsed body before destructuring it; keep malformed input within a 4xx response.

Source: [login route](../../src/app/content/api/login/route.ts).

### 11. P2 — Approvals overflows on a 320px screen

**Reproduce:** open Approvals at 320px. The document becomes **377px wide**, creating 57px of page overflow. The 390px check passed.

**Impact:** a smaller phone requires sideways scrolling to inspect the approval list.

**Action:** adjust the approval-list/KPI layout for narrow widths and recheck at 320px, including long titles, lane badges and age labels.

Evidence: [320px screenshot](qa-2026-11-15/approvals-320px.png).

### 12. P2 — Approval feedback has no persistent field label

**Evidence:** the review-note textarea has a placeholder but no associated label or ARIA label. The browser exposes the placeholder as its fallback name.

**Impact:** the instruction disappears while the user types, and the field's purpose is less stable for assistive technology.

**Action:** add a visible label for the reason/note field and retain the optional-detail hint separately.

Source: [approval note](../../src/app/content/_components/editors.tsx).

### 13. P2 — The health probe passes while production refuses the workspace

**Reproduce:** on the temporary production server, `/content` returned 503 while `/content/api/healthz` returned 200 with `{"ok":true}`.

**Impact:** a monitor using only this probe can report the deployment healthy when no workspace user can enter. The endpoint currently checks database connectivity, consistent with its code comment.

**Action:** distinguish a database/liveness probe from application readiness, or include required configuration in the readiness decision.

Sources: [health probe](../../src/app/content/api/healthz/route.ts), [middleware](../../src/middleware.ts).

## Navigation and ease of use

The section names, grouped sidebar, consistent headings, starter prompts, disabled empty actions and “How this page works” disclosures give users useful orientation. The command palette found every client section. Real saves refresh server data, failures remain visible after the loader closes, and changes/rejections require a reason. These are strong foundations.

The larger problem is completing a task across sections. A user must understand signals → topics → selection → drafting → quality check → approval → design → scheduling, while some promised transitions are absent or hidden. “Approve” does not explain how to resolve missing evidence, and “Draft them now” omits the step that delivers the promised approval queue. The current brand kit also reports incomplete audience/themes; that is an operator setup gap and can affect output quality.

| Technical UX dimension | Provisional score | Reason |
|---|---|---|
| Accessibility | 1/4 | Contrast, drawer focus and feedback labeling need work. |
| Performance | 2/4 | No browser runtime exceptions; sampled development navigation took about 0.09–3.56s. Production user performance/Core Web Vitals were not measured because workspace readiness is blocked. |
| Responsive design | 2/4 | Most checked widths work, with narrow approval overflow and hidden sign-out. |
| Theming | 3/4 | Consistent intentional light theme and shared tokens; semantic text colors need correction. Absence of dark mode is not treated as a defect. |
| Implementation integrity | 2/4 | Reused UI/action patterns are coherent, but proof resolution and draft-to-approval guidance do not match the available workflow. |
| **Total** | **10/20** | **Significant work needed; this is a heuristic score, not a release certification.** |

The Impeccable detector was run and its design-pattern warnings reviewed. Its aesthetic warnings were not counted as functional defects. The report prioritizes reproduced operational and usability problems.

## Coverage limits and retest order

1. Restore adequate provider credits and reachable Postiz, then set production-safe secrets.
2. Fix proof resolution and the draft → QC → approval handoff.
3. Repeat one controlled live journey: capture → research → score → select → draft/script → QC → human review → creative → controlled scheduling → external confirmation → analytics.
4. Check paid competitor scrapes on each intended platform, actual remote-video downloads, YouTube after configuration, complete fresh-account onboarding, and longer-running jobs/recovery.
5. Address drawer accessibility, contrast and mobile controls; rerun responsive checks. Use `/impeccable harden`, `/impeccable adapt`, and `/impeccable clarify` for the corresponding fixes, then `/impeccable polish` after functional checks pass.

**Not certified:** successful live social publication, Postiz rescheduling/cancellation, fresh post analytics, full paid scrapes, successful image generation, a newly generated complete script, all onboarding branches, every data-dependent repeated button instance, every possible function input, load/concurrency behavior, every browser/screen reader, or production Core Web Vitals. A representative repeated component was exercised rather than mutating every existing content item.
